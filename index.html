Postmortems

Opinions I've earned the hard way, written down so you know what you're hiring.

Note 01

A payment retry is only safe if it's idempotent

Gateways time out. Networks drop mid-response. The dangerous case isn't the failure — it's the retry that succeeds twice. So every write on a money path gets a client-supplied idempotency key, stored with the result of the first attempt, and a replay returns that stored result instead of executing again.

The corollary is that the key has to be generated upstream of the failure, by the caller, before the request is ever sent. Generating it inside the service is a bug that looks like a feature until the first duplicate disbursal.

Note 02

Cache the read path, never the ledger

Redis in front of hot reads is the cheapest latency win available — reference data, rate tables, session and permission lookups all tolerate a few seconds of staleness. Balances and transaction history do not. The line I hold: anything a regulator could ask me to reconstruct is read from the source of truth, every time.

Which means the real design work is invalidation, not caching. Write-through where correctness matters, short TTLs where it doesn't, and an explicit answer to “how stale can this be?” for every key before it ships.

What kind of role are you looking for? +

Senior or lead backend engineering. The domain matters less than the problems: systems where correctness and reliability are hard requirements, whether that's payments, commerce, logistics, or infrastructure. I like owning a service end to end — design, delivery, and the pager.

Why so much fintech on this page? +

It rewards the engineering I actually enjoy. Idempotency, audit trails, reconciliation, and careful error handling matter far more when the failure mode is financial rather than cosmetic.

How do you approach a legacy monolith? +

Find the seams that follow real business boundaries, extract the one with the clearest contract first, and keep it boring. I migrated a monolith to services at Kellton by shipping incrementally, never with a big-bang rewrite.

Do you work with frontend or infra teams? +

Constantly. I write the API contracts frontend depends on and own the AWS pieces my services run on — Lambda, ECS, S3, CloudWatch, Athena — so I can debug across the boundary instead of filing a ticket.

Do you mentor? +

Yes. I run code reviews and coach engineers on backend design and code quality. The best review comment is the one that stops a bad abstraction before it has three callers.

How do you test money paths? +

Integration tests around the payment flows first — including replaying the same request twice to prove idempotency holds — with gateway sandboxes standing in for the real thing. Unit coverage matters, but on money paths the bugs live between services, not inside functions.

What are you learning right now? +

Deeper event-driven patterns and the operational side of running services at scale — the gap between a system that works and one that stays working under load.
